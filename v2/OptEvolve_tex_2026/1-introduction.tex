\section{Introduction}
\label{sec:introduction}

Choosing and tuning a solver for a class of convex problems is usually described as a
search problem. It is first a measurement problem. At its shipped defaults the fastest
solver for total-variation denoising in our comparison field returns in $0.023$\,s and
reaches no accuracy target at any image size; on cell-type deconvolution
\texttt{scipy.nnls} returns faster still and does not satisfy the equality constraint at
all. Ranked by wall clock, both win. In three of the six application classes,
at least one packaged baseline returns a point that fails the common
target-accuracy check.
Automating solver design is stymied by three distinct obstacles, and this is
the first.

\textbf{(i) A comparison cannot be trusted when every solver grades itself.} Reported
times are times to each library's own stopping rule, so they are not commensurable, and
a field missing the structure-specific specialist flatters whatever remains.
\textbf{(ii) A fast generated iteration need not be a convergent one.} Timing
LLM-proposed code establishes that it was quick on the instances tried, not that it
converges, and no amount of benchmarking closes that gap.
\textbf{(iii) The decisive choices span formulation, algorithm, and hardware, and they
interact.} Moving a constraint into a projection changes the iteration count; the
iteration count changes which device wins; the device changes which algorithm is
cheapest per step. Tuning any one axis alone finds the wrong design.

A splitting method handles parts of an objective through simpler updates, such as a gradient step and projection onto a constraint set. Their composition is an \emph{operator} mapping the solver's current state to its next state. Choosing that composition changes both convergence conditions and work per iteration; setup, compilation, and device placement further affect wall time. Since 2021, PDLP has combined primal--dual splitting with preconditioning, adaptive steps, and restarts; RLQP learns QP penalty updates; and HPR-LP combines another splitting scheme with adaptive policies \citep{Applegate2021Practical,Ichnowski2021Accelerating,Chen2024HPRLP}. LLM-driven search, notably FunSearch and AlphaEvolve, offers a way to propose further designs \citep{RomeraParedes2023Mathematical,Novikov2025AlphaEvolve}. Yet timing generated code cannot prove convergence, and a fast update need not beat a recognized specialist on the full solve. The question is how to search these design choices jointly while checking mathematical conditions and evaluating implementations and competing routes separately.

We introduce \textbf{OptEvolve}.\footnote{Anonymized code, genomes and reproduction scripts: \url{https://anonymous.4open.science/r/OptEvolve-8104/README.md}} Given a structured convex problem family, training instances, a target accuracy, and available devices, it searches solver formulations and implementations under a pre-execution convergence gate, then routes new instances using measured time to a common original-problem accuracy check on the target hardware. A typed genome specifies a splitting scheme, parameters, solution-preserving formulation, projection implementation, and CPU or GPU backend. Before timing a candidate, a symbolic gate checks sufficient convergence conditions for five exact base schemes and admissible relaxations; synthesized projections and kernels undergo separate finite numerical tests. The theorem covers the stated exact splitting-iteration grammar, not arbitrary generated code or the adaptive policies of PDLP, RLQP, and HPR-LP. A high-accuracy numerical reference used by the final acceptance check is not itself a formal proof of optimality.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{Pre-execution convergence gate, for (ii).} Under the stated assumptions, every admitted scheme in the exact splitting-iteration grammar converges: the gate checks sufficient construction conditions \emph{before} execution (Theorem~\ref{thm:soundness}). Numerical implementations are tested separately.
\item \textbf{Joint solver and hardware search, for (iii).} Search couples schemes and parameters with solution-preserving formulations, contract-tested projection implementations, and measured per-device costs; routing can defer to an existing specialist. Tested synthesized projections meet the target on $9/9$ unseen instances versus $5/9$ for an unchecked faster implementation (Section~\ref{sec:exp:evolve}). The best fused GPU tile changes across devices (Section~\ref{sec:exp:llm}).
\item \textbf{End-to-end gains and their boundary.} On budget-constrained least squares at $n=48{,}000$, with no packaged specialist for this family, a searched formulation and projection give a $25.22\times$ faster cold solve at $10^{-4}$ than the fastest accepted engine at shipped defaults (Appendix~\ref{app:generated}); a separate $n=12{,}000$ ablation shows that formulation accounts for most of this family's gain. On held-out QP, LP, and SOCP instances the router solves $27/28$ within budget versus $26/28$ for a best-per-instance oracle restricted to existing competitor engines; first-visit exploration remains costly (Section~\ref{sec:exp:llm}). With expert hints withheld, the loop also assembles the unmixing method, but uniform random search reaches an equivalent method in one seed, so these runs do not establish an LLM advantage (Section~\ref{sec:exp:recover}).
\item \textbf{Independent evaluation, for (i).} We release the OptEvolve-Bench protocol and measured field. Each result faces the same original-problem acceptance check rather than a solver's own stopping rule, comparisons include recognized structure-specific specialists, and the finest accepted tolerance is reported beside time. The release pairs six application classes at packaged-solver defaults with $806$ acceptance records over $14$ engines on Netlib, Maros--M\'esz\'aros, and generated LP, QP, and conic instances. The accuracy check changes the wall-clock verdict on three of the six application classes (Section~\ref{sec:exp:regimes}).
\end{itemize}
